# 风控与签名策略

这份文档解释两件事：**为什么不做接口签名**，以及**遇到风控时这套工具怎么活下来**。

## 一、京东 H5 的签名是什么

`m.jd.com` / `item.m.jd.com` 的下单链路（预约、加购、结算、提交订单）在请求头里带两类动态参数：

- `h5st`：一串用页面内 JS 运行时算出来的指纹串，包含时间戳、页面随机种子、设备信息、请求体摘要。
- `sign` / `body` 签名：部分接口对请求体做二次摘要。

特点：

1. **每请求都变**，且与页面加载时注入的种子绑定。
2. 算法在混淆过的 JS 里，会随版本更新。
3. 算错的请求不是「403」这么简单，常见是返回「系统繁忙」并给账号打一个风险标记。

所以「抓包 → 复刻请求 → 批量刷」这条路，维护成本是一个版本一次逆向，且失败是静默的（你以为在抢，其实早就被标记了）。

## 二、本工具的路线：页面内自动化

```
原生（Kotlin）                     页面（WebView）
─────────────                     ──────────────
闹钟 / 校时 / WakeLock   ──注入──▶  autopilot.js
                                    │
收事件 ◀── __LCS_NATIVE.post ───────┤ 找按钮 → 合成 touch → 点击
                                    │
                                  签名由页面自己的 JS 生成
```

- 点击发生在真实页面里，`h5st` 由京东 JS 自己算，**架构上不存在签名不一致**。
- 代价：依赖 DOM。所以词典用「文本匹配」而不是 CSS 选择器 —— 京东改版会改 class，但「立即抢购」这四个字很少变。
- 再兜一层：`probe()` 把当前页所有可点元素文本吐给原生，改版时 30 秒就能把新词加进 `TXT`。

## 三、行为风控的三个维度与对策

| 维度 | 京东在看什么 | 本工具怎么做 |
|---|---|---|
| 节奏 | 点击间隔是否稳定到像机器（固定 100ms 连点最可疑） | `jitterMinMs/MaxMs` 60–260ms 随机；`tapIntervalMs` 600ms 闸门防重复跳转；4 个页面按 60ms 错开 |
| 事件真实性 | 有没有 `touchstart/touchend`、坐标是否合理 | `synthTouch()` 用 `TouchEvent` 构造真实触摸序列并派发，`el.click()` 只作兜底 |
| 设备指纹 | UA、`__jda` 等 cookie、屏幕参数是否前后一致 | **不改 UA、不清 Cookie、不换 WebView 实例**；Cookie 与登录态由系统 CookieManager 统一持有 |

反面做法（都别做）：改 UA 伪装京东 App、每轮清 Cookie 换身份、5 个以上 WebView 并发、多账号轮询同一活动。

## 四、验证码分级

| 类型 | 触发场景 | 处理 |
|---|---|---|
| 无感验证 | 高频访问 | 通常静默通过；若返回「系统繁忙」，本工具记为 `stalled` 并放慢到 800ms |
| 滑块 / 图形 | 提交订单前后 | `RiskGuard` 检测到 `安全验证` / `拖动滑块` → **暂停自动点击**，界面提示人工，过完点「手动开火」续跑 |
| 短信 / 人脸 | 大额或异常设备 | 工具无能为力，只能人工。日志会停在 `authExpired` 或 `risk` |

`manualCaptcha: true` 是默认值。设成 `false` 只会让脚本在验证页上空转，不会提高成功率 —— 因为验证页里根本没有可点的抢购按钮。

## 五、频率红线（自用设定）

| 项 | 值 | 理由 |
|---|---|---|
| 账号数 | 1 | 多账号同设备是风控最强信号 |
| 设备 | 1 台手机 | 换设备会重置指纹，反而更可疑 |
| 并发页面 | ≤ 4 | 再多 CPU 抖动会让首次点击延后几百毫秒，得不偿失 |
| 单 SKU 重试 | 90 秒窗口内，同一按钮 ≥600ms 间隔 | 重复点击会让页面重复跳转，把已进入的结算流程打回 |
| 单日场次 | 按活动 5 场 | 不额外刷接口 |

## 六、失败模式与判断

| 日志 | 含义 | 是不是风控 |
|---|---|---|
| `done reason=soldOut` | 页面出现「已抢完/无货」 | 否，纯库存 |
| `done reason=timeout` | 90 秒内一直没点到目标按钮 | 可能页面没加载完，也可能按钮文案变了 |
| `stalled` | 同阶段点了 12 次还没前进 | 页面结构变了 / 按钮被遮挡 |
| `risk` + `paused` | 命中验证页 | 是，人工接管 |
| `authExpired` | 取不到 `pt_key` | 否，登录过期 |
| `error` | JS 抛异常 | 否，注入或页面兼容问题 |

判断原则：**先看 `stage`**。`stage` 一直是 `ITEM` 说明根本没进到结算，问题在商品页；`stage` 到 `SETTLE` 才失败，问题在提交环节（多为风控或地址/支付方式缺失）。

## 七、为什么停在收银台

- 提交订单后京东会跳收银台，支付需要密码/指纹/面容，WebView 里做不了也不该做。
- 自动支付是最强的风控信号之一（异地、非常规操作路径、无生物识别）。
- 人工付款 10 秒，赌账号被封不划算。

所以 `ui.autoPay` 字段存在但**永远不生效**，只是把「不做」写进配置里，避免以后有人误加逻辑。

## 八、改版应对清单

京东改版时按顺序查：

1. 「诊断当前页」看 `stage` 与 `buttons`；
2. `stage` 不对 → 改 `detectStage()` 的判据（现在靠 `提交订单` 判结算、`全选`+`去结算` 判购物车）；
3. `buttons` 里没有目标词 → 改 `TXT` 词典；
4. 点击没反应 → 看是不是 iframe / 新窗口，`setSupportMultipleWindows(false)` 已禁用弹窗，若是 iframe 需要在 `allElements()` 里下钻 `contentDocument`（同源才行）；
5. 全都不行 → 换活动页 URL 或改用手动模式（关掉 `autoSubmit`，只做提醒与预填）。
